# 接口文档生成规范（SOP）

> 本规范固化 GCSJ 灾害预警系统后端 Controller 接口文档的统一生成流程与格式。
> 首个范本：`接口文档-AlertController.md` + `AlertController-功能流程结构图.drawio`。
> 后续每个 Controller 模块均严格按本规范产出，保证全项目文档风格一致、可检索、可二次编辑。

---

## 一、产出物清单（每个 Controller 固定两份）

| 产出物 | 命名规范 | 说明 |
| --- | --- | --- |
| 接口文档 | `接口文档-{XxxController}.md` | 主文档，图文一体，含功能表/流程图/实体表/DTO·VO |
| 流程图源文件 | `{XxxController}-功能流程结构图.drawio` | iodraw / draw.io 可直接打开二次编辑的矢量图 |

- 文件统一放在 `M:\GCSJ-4\docs\` 下。
- **一个 Controller 一份 md**（不汇总成单一总文档），便于解耦、并行编写、改动互不影响。
- 后续可再补一份 `README.md` 作为总索引，串联各模块文档。

---

## 二、md 文档结构（四节固定顺序）

每份接口文档严格按以下四节展开：

### 第一节 · Controller 功能表

照搬用户指定的表格骨架，**每个方法占四到五行**：方法签名 → 功能 → 输入 → 输出 →（保留）路由。

| 类功能 | {模块}功能（一句话概括该 Controller 的业务职责） |
| --- | --- |
| **方法一** | `方法名(参数类型)` |
| | 功能：一句话说明该方法做什么、触发了什么副作用 |
| | 输入：请求体 / 路径参数 / 查询参数，列出关键字段 |
| | 输出：`Result<T>` 的具体 T 类型与含义 |
| | 路由：`HTTP方法 完整路径` |
| **其他方法** | 与上面结构一致 |

> **路由行为规范保留项**：每个方法必须标注 `GET/POST/... 完整路径`，方便接口定位与前后端联调。

### 第二节 · 功能流程结构图

- md 内嵌 **Mermaid** 代码块（图文一体，markdown 预览即可看图）。
- 同时产出独立 **`.drawio`** 文件（iodraw/draw.io 二次编辑）。
- 形状约定（两种形式都遵守）：

| 形状 | 含义 | Mermaid 写法 | drawio 样式 |
| --- | --- | --- | --- |
| 圆角胶囊 | 开始 / 结束 | `(["..."])` | `rounded=1;arcSize=50`（蓝） |
| 矩形 | 处理步骤 | `["..."]` | `rounded=0`（橙） |
| **棱形** | **判断 / 分支** | `{"...?"}` | `rhombus`（黄） |
| 平行四边形 | 输入 / 输出（DTO·VO） | `[/"..."/]` | `shape=parallelogram`（紫） |
| 圆柱 | 数据存储（表/外部实体） | `[("...")]` | `shape=cylinder3`（灰） |

- 分支判断**必须用棱形**，每条分支出线标注条件（是/否或具体取值）。
- 写库回流、可选路径用**虚线**表示。

### 第三节 · Entity 实体表

列出对应数据库表（含 schema，如 `biz.biz_alert`），字段表至少包含：

| 字段 | 类型 | 列名 / 约束 | 说明 |

- 必须包含继承自 `BaseEntity` 的公共字段：`id` / `deleted` / `createdAt` / `updatedAt`，并注明「继承自 BaseEntity」。
- 特殊类型要点明，如 `Point → geometry(Point,4326)`（PostGIS）、逗号分隔串等。

### 第四节 · 关联 DTO / VO

把接口「输入/输出」的具体字段讲清楚——业务功能才算说透。

- **入参 DTO**：字段 / 类型 / **校验注解** / 说明（如 `@NotBlank`、`@Min/@Max`、`@Pattern`）。
- **出参 VO**：字段 / 类型 / 说明，注明派生字段来源（如 `channels` 由 entity 逗号串拆分、`levelLabel/levelColor` 为前端展示加工）。

## 三、生成流程（每个模块照此执行）

1. **读源码**：依次读取 `controller/{XxxController}.java`，再顺藤摸瓜读其依赖的 `dto/`、`vo/`、`entity/`、必要时 `service/` 接口，确保输入输出与业务逻辑准确。
2. **写功能表**：逐方法提取 `@Operation` 摘要 + 方法签名 + 路由 + 入参/出参，落成第一节表格。
3. **梳理主流程**：从「入口 → 核心处理 → 状态流转 → 查询/展示」主线归纳，画 Mermaid 内嵌进 md（第二节）。
4. **出 drawio**：把同一流程用矢量形状落成 `.drawio`，棱形表判断，配色用 draw.io 标准色。
5. **补实体表与 DTO/VO**：第三、四节，讲清字段语义与校验。
6. **核对**：比对源码字段与文档是否一致；流程图分支是否覆盖代码中的条件路径（如 source 来源、channels 是否为空、status 流转）。
7. **交付**：md + drawio 两份均落到 `docs/`，提供 computer:// 链接。

---

## 四、术语与约定

- 统一返回包装 `Result<T>`；分页用 `Result<PageResult<T>>`。
- 路径基于各 Controller 的 `@RequestMapping` 前缀。
- 业务推断（如 status 具体取值、是否允许跳过某步）若源码未明示，文中标注「按 controller 语义推断」，待 Service 校准。
- 中文为主，类名/方法名/字段名/路由保留英文原文。
